# ADR-016: The boundary between the backend and the quant layer

**Status:** Accepted · **Date:** 2026-08-28 · **Phase:** Research Foundation Upgrade (U10)

## Context

[ADR-004](ADR-004-python-quant-layer.md) chose Python for the quantitative
layer and left one thing explicitly open:

> **Open:** how the backend and the quant layer exchange work — shared database,
> job queue, or local service — is a Phase 8 decision, taken when there is a
> real workload to size it against.

That workload now exists in outline. The Research Foundation Upgrade produces
canonical datasets in the backend and consumes them in Python; research runs
must be triggerable, their results must be recorded, and a failing experiment
must not be able to affect the API.

Two constraints come from ADR-004 itself: research code and request handling
have different change rates and different reliability requirements, and the
layers must not drift apart in their understanding of the data model.

## Decision

**PQT exports, Python consumes, PQT records.** Three channels, each with one
job:

| Channel | Carries |
| --- | --- |
| **PostgreSQL, read-only** | Exploration and reference data |
| **Parquet datasets with a hashed JSON manifest** | Anything that must be reproducible |
| **A `research.jobs` table polled by a worker** | Work requests |

Python writes only into the `research` schema. The backend owns every migration,
including the `research` schema's.

The boundary is enforced by a database role: `quant_research` holds `SELECT` on
the `quant` schema and **no write grant**, and full rights on `research`. The
test that proves the boundary is the one asserting an `INSERT` into
`quant.bars` from that role is **denied**.

A `quant-worker` container runs the research process. It claims jobs with a
lease, so a crashed worker's job becomes claimable again rather than lost.

The dataset manifest is a JSON document governed by a JSON Schema, generated by
the backend and validated by Python on load.

## Alternatives

| Option | Latency | Complexity | Failure isolation | Type safety | Reproducible |
| --- | --- | --- | --- | --- | --- |
| Shared PostgreSQL, read | ms | none | total | schema-level | high |
| Parquet export | batch | low | total | manifest + schema | highest |
| Job table + worker | seconds | low | total | schema-level | high |
| gRPC | sub-ms | high | good | strong | medium |
| REST | ms | medium | good | weak | medium |
| Message broker | ms | high | good | weak | medium |
| Subprocess launched by the API | — | medium | poor | none | low |
| Embedded Python in the API process | µs | high | none | none | low |

## Reasoning

**Embedded Python is rejected outright.** A failing experiment would take the
API down, which is the precise outcome ADR-004 chose a separate layer to
prevent. Adopting it would reverse a decision without a new reason.

**Subprocesses launched by the API** put research failures in the API's process
tree and give no isolation worth the name.

**gRPC and REST** couple request lifetimes to research runtimes and add a
service to deploy, in exchange for a latency property nothing currently needs.
Research jobs run for minutes; sub-millisecond transport is not the constraint.
The right time to revisit gRPC is Phase 18, when online serving creates a
genuinely synchronous need.

**A message broker** is new infrastructure — another container, another failure
mode, another thing to operate — for a queue whose depth will be single digits.
A table in a database that is already there does the same job and is
transactional with the data the job refers to.

**Parquet with a hashed manifest** is the choice that carries reproducibility.
A dataset version becomes a file with a checksum: it can be copied, archived and
verified. A dataset version that is a database state cannot be any of those
things, and "the result came from the database as it was in March" is not a
statement anyone can act on.

The manifest with a JSON Schema also closes the drift ADR-004 flagged as a
trade-off. Rather than two hand-maintained models, there is one generated
contract and a validation step that fails loudly.

The decision is deliberately boring. It buys total failure isolation, exact
reproducibility and zero new infrastructure, and it defers the interesting
options until something needs them.

## Trade-offs

- Polling latency of seconds. Irrelevant for minute-long research jobs; would be unacceptable for online serving, which is why that is a separate future decision.
- Two systems read the same PostgreSQL instance. Bounded by the read-only role and by the fact that research reads are analytical and infrequent.
- Parquet export duplicates data that already exists in PostgreSQL. That duplication *is* the immutability, and it is the point rather than a cost.
- A job table is a queue implemented in a database, which has known limits at high throughput. Those limits are orders of magnitude above this workload; if that changes, a broker becomes justified and gets its own ADR.
- The database role must be provisioned in every environment, including a developer's laptop, or the enforcement is theatre.

## Consequences

- Python **may not write** `quant.*`. Enforced by grant, tested by a denial assertion.
- Python **may not fetch from a market data provider**. Ingestion belongs to the backend; a research process that fetches its own data produces results nobody can reproduce, because the data would not belong to a dataset version.
- The backend owns all migrations, including `research`.
- `docker-compose.yml` gains a `quant-worker` service. A crashing worker must never affect API health, and a test asserts it.
- Every research result is traceable to a dataset version, a code commit and a research engine version.
- This ADR closes the open question in [ADR-004](ADR-004-python-quant-layer.md). ADR-004 is not edited; it is superseded on that point by this record.
- **Open:** the transport for online serving (Phase 18). Revisit gRPC then, with a workload to size it against — the same discipline ADR-004 applied here.
